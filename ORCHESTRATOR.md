# Инструкция оркестратору (ночной режим)

Ты оркестратор: режешь работу на подзадачи, раздаёшь воркерам, принимаешь по критериям. Сам код пишешь только если подзадача мелкая. Правила `CLAUDE.md` действуют и здесь.

## 1. Бюджет недельного лимита

Перед **каждым** запуском воркера и после каждой приёмки вызывай `get_usage` (инструмент `mcp__ccd_session_mgmt__get_usage`). Смотри два окна:

| Окно | Правило |
|---|---|
| Weekly · all models | порог дня: Пн 20%, Вт 40%, Ср 60%, Чт 80%, Пт 95% (день недели по времени сервера) |
| 5-hour limit | если ≥ 80%: новых воркеров не запускай, жди `resetsAt` |

- `percentUsed` недели ≥ порога дня: **стоп**. Новых воркеров нет, уже запущенных дождись, запиши итог в журнал, заверши цикл.
- До порога осталось меньше 3 процентных пунктов: запускай только одну подзадачу за раз.
- Если `get_usage` вернул `unavailable` или `not_applicable`: считай бюджет исчерпанным, останови запуск новых воркеров и запиши причину в журнал.
- Суббота и воскресенье: работу не начинай, если пользователь не разрешил явно.

## 2. Очередь задач

- Задачи лежат в `tasks/queue.md`: нумерованный список, у каждой статус `[ ]` / `[x]` / `[!]` (требует решения человека).
- Бери первую невыполненную. Если в ней нужен выбор пользователя (данные в БД, схема, коммит, удаление), пометь `[!]`, запиши вопрос и иди дальше.
- **Зависимости:** если задача опирается на другую, в очереди пишется `зависит от № N`. Если № N получила `[!]`, зависимые задачи пропускаются (в журнал: «пропущена, ждёт № N»), независимые продолжаются. Задача без указанных зависимостей считается независимой.
- Запрещено без явного «да» пользователя в очереди: запись в БД, создание таблиц, `git commit`, `git push`, удаление данных, правка `.env`.

## 3. Подзадача для воркера

Каждый воркер получает короткую спецификацию:

1. **Цель** одной фразой.
2. **Файлы**, которые можно менять (остальные не трогать). Два воркера не получают один файл одновременно.
3. **Критерии приёмки**: проверка вёрстки `/check-layout`, пересборка контейнера по `CLAUDE.md`, страница открывается без ошибок в консоли, дифф без лишнего.
4. **Формат отчёта** (не длиннее 10 строк): что сделано, список файлов, результат проверок, что не удалось.
5. **Запрет**: не расширять задачу, не коммитить, не менять файлы вне списка.

Модель воркера: `haiku` или `sonnet` для механики (правка текста, стили, справка), `opus` только для сложной логики. Изоляция: `worktree`, если воркеров больше одного.

## 4. Параллельность

- Не больше **2** воркеров одновременно (3 только при запасе ≥ 15 пунктов до порога дня).
- Параллельно запускай только задачи с разными файлами. Основные общие файлы (`index.html`, `main.py`, `history.py`) трогает один воркер за раз.

## 5. Приёмка

После отчёта воркера проверь сам:
1. `git diff --stat`: только разрешённые файлы.
2. Пересборка и проверка по разделу «Автоматическое тестирование» в `CLAUDE.md`.
   Прогон тестов: `cd tests && python -m pytest -q` (нужен запущенный `postgres_db`). **Без зелёного прогона задача не считается сделанной.** Красный тест возвращается воркеру как есть.
   Воркеру **запрещено менять и удалять существующие тесты**: изменение теста возможно только по явному «да» пользователя. Новые тесты воркер добавлять может (ошибка сначала воспроизводится тестом, см. «Тесты» в `CLAUDE.md`).
   **Пересборка в режиме 2** без `down` (он требует подтверждения): `docker compose build --no-cache fastapi-api`, затем `docker compose up -d fastapi-api` (`up -d` сам пересоздаёт контейнер). Это заменяет первый шаг из `CLAUDE.md` и из `/check-layout`.
   **Вёрстка** (правки `fastapi-api/static`): воркеры, правящие код, браузер и пересборку контейнера **не используют** (браузер и контейнер общие). Проверку делает **один проверочный воркер за раз, строго после** остальных кодовых воркеров: пересобирает контейнер (`build --no-cache`, затем `up -d`, без `down`), открывает встроенный браузер и проходит `/check-layout` (минимум 1920, 1366, 955; для шапки и Andon все размеры, включая режим «архив» и ширину до 1700px), в отчёте `overlaps` пуст, нет нового `clipped` и `hscroll`, и присылает скриншоты. Оркестратор принимает отчёт. Экраны, требующие входа администратора, воркер проверить не может (пароль не передаётся): такие проверки идут как `[!]` с чек-листом пользователю. Если встроенный браузер недоступен (запрос разрешения, нет связи с `localhost:8000`), задача получает `[!]`.
3. Все критерии из спецификации выполнены, иначе вернуть воркеру на доработку (**не больше 2 раз**), затем `[!]` и переход к следующей задаче (не остановка очереди).
4. Принятое оставляй в рабочей папке **без коммита**: коммит делает пользователь после проверки.
5. **Изоляция застрявшей работы:** правки задачи со статусом `[!]` остаются в её worktree и **не попадают в основную папку**; другим воркерам этот worktree не даётся. В журнал: путь worktree, красные тесты, что пробовал воркер, предполагаемая причина.

## 6. Журнал

После каждого шага дописывай строку в `orchestrator-log.md`:

`ГГГГ-ММ-ДД ЧЧ:ММ | задача № | воркер/модель | результат (принято / доработка / [!]) | недельный % | 5-часовой %`

В конце цикла добавь итог: что принято, что ждёт решения, почему остановился (порог, 5-часовое окно, очередь пуста, ошибка).

## 7. Цикл и ожидание

- Работай шагами, между шагами не крутись впустую. Если ждёшь сброс окна или воркера, планируй ожидание (`ScheduleWakeup` в режиме `/loop`) не короче 20 минут.
- При ошибке окружения (контейнер не поднимается, нет связи с БД) не чини вслепую: запиши в журнал и остановись.
- Контекст сессии: если занято > 80% окна, дай краткое резюме в журнал и заверши цикл, чтобы не потерять состояние при сжатии.

## 8. Утренний отчёт

В последнем сообщении цикла: список принятых задач, список `[!]` с вопросами, недельный процент, рекомендация, что проверить и коммитить первым.
