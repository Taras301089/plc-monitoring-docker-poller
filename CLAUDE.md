# CLAUDE.md — Инструкции для Claude Code

Система называется **PMM (Production Monitoring & Management)**, по-русски «Мониторинг и управление производством»: опрос ПЛК, доска Andon/KPI, простои, отчёты, графики, тренды. Названия папок, контейнеров и базы (`plc-monitoring-docker-poller`, `general_data_hub_BD`) не переименовываются.

## 📚 Подробные правила: читать перед работой над темой

Здесь только общие правила работы. Правила по темам лежат в отдельных файлах (так каждая сессия и каждый воркер не читают лишнее):
- **`docs/rules-ui.md`**: экран и вёрстка (стиль, подсказки `title`, таблицы как в Excel, надписи, большие списки, экономия высоты, адаптивная вёрстка, шрифты, цвета, порядок элементов, настройки в интерфейсе, удаление записей, «содержание, затем автор», колонка «Причина», вкладка «Переменные ПЛК», справка). **Прочитать перед любой правкой `fastapi-api/static/` и любым новым элементом интерфейса.**
- **`docs/rules-reports.md`**: числа и расчёты (идентичность данных), период, Excel-выгрузки, имена файлов. **Прочитать перед любой правкой расчётов, отчётов, графиков, Excel и данных из ПЛК.**
- Оркестратор в подсказке воркеру называет, какие из этих файлов прочитать.

Самое главное из них (чтобы не нарушить, даже если файл не открыт):
- у каждого нового элемента `title` 10–20 слов; акцентных цветов три (зелёный, красный, синий), жёлтый не использовать; размеры шрифта только из `--fs-small/--fs-large/--fs-title`
- никаких наложений блоков, шапка не ломается на 955px, после правки вёрстки проверка `/check-layout`
- одно число везде одинаковое: считает одна функция на сервере, экран, отчёты и Excel берут из неё; тайм-аут запроса 6 с; данные перечитываются сами
- Excel повторяет экран (те же плитки, графики, таблицы, названия, порядок), это проверяет тест
- экраны с данными работают за период: «День», «Неделя», «Месяц», «Прошлый месяц», «С»/«По», ◀ ▶
- большие таблицы как в Excel (сортировка, фильтры, копирование, ширина колонок `attachColWidths`)
- настройка из БД видна в интерфейсе, право проверяется на сервере; удаляет только автор и администратор, история сохраняется

## 📋 Управление задачами

**Когда даете список задач:**
- Структурируйте задачи нумерованным списком в одном сообщении
- Я буду выполнять по одной и отслеживать статус
- После выполнения каждой задачи отчитываюсь и жду вашей проверки; commit делаю только после подтверждения (см. раздел «Пошаговое выполнение»)
- В конце покажу чеклист всех выполненных работ

**Пример:**
```
Задачи:
1. [ ] Убрать id из селектора, показать IP и статус
2. [ ] Перевести интерфейс на русский
3. [ ] Переименовать табы навигации
4. [ ] Добавить индикатор подключения
```

**Приоритеты:**
- Первый запрос: обновляю/добавляю этот раздел в MD
- Каждая проверенная и подтверждённая задача: один commit (после вашего согласия)
- Тестирование: после каждого изменения загружаю в браузер и проверяю

## 🔀 Режимы работы

1. **Пошаговый (по умолчанию):** пользователь за ПК, действуют правила раздела ниже
2. **Оркестратор и воркеры:** пользователь на работе и не может следить; правила в `ORCHESTRATOR.md`, очередь задач каждого разработчика в своём файле `tasks/queue-<имя>.md` (`queue-taras.md`, `queue-almat.md`, `queue-server.md`), общие идеи в `tasks/roadmap.md`, закрытое в `tasks/done.md`; плановый запуск на ПК берёт задачи только из файла этого ПК. Запускается автоматически **в 16:25 каждый день, включая выходные, если позволяет недельный лимит** (время ПК; плановая задача `orchestrator-night`; в выходные порог лимита 95%, подробности в `ORCHESTRATOR.md`), если в очереди есть невыполненные задачи; фразой «режим оркестратора» можно запустить вручную. Коммит и push в этом режиме не делаются: результат ждёт проверки пользователя. Задачи, где нужно решение пользователя (данные в БД, расписание Windows, схемы, перенос на сервер), помечаются `[!]` и не выполняются
- **Для каждой новой задачи сначала определяется, можно ли делать её в фоне** (воркером), и пользователю сообщается один из трёх исходов:
  1. **Можно в фоне:** задача проверяется тестами, не требует решений пользователя, входа или ручной проверки; запускается воркер, результат принимает оркестратор по тестам
  2. **В фоне можно, если будет выполнено условие:** называется, что нужно от пользователя (решение, согласие на схему БД или правку поллера, вход администратором, доступ, уточнение вида), и после этого задача запускается
  3. **В фоне не получится:** называется причина (например, нужна визуальная проверка на устройстве, ввод пароля, физический доступ к ПЛК или телевизору, правка вёрстки с подбором по скриншотам); задача выполняется вместе с пользователем в обычном режиме
- **Исход называется первой строкой ответа ДО начала работы, даже для маленьких задач** («Исход 1/2/3: …»); без этого работа не начинается. Если исход 1 или 2, запускается воркер (оркестратор проверяет результат); если оркестратор всё же делает задачу сам (например, правка в одну строку после диагностики), это называется явно с причиной, а не молча
- Правка вёрстки идёт **целиком в фоне**: воркеры правят CSS и JS без браузера, затем **один проверочный воркер за раз, после остальных**, пересобирает контейнер и проверяет вид во встроенном браузере (`/check-layout`, скриншоты); браузер и пересборка контейнера общие, поэтому параллельно ими пользоваться нельзя. Исключения: экраны, требующие входа администратора (пароль воркеру не передаётся), телевизор и реальные устройства; это исход 3 или чек-лист пользователю
- Автозапуск настроен как локальная процедура «Режим оркестратора» (`orchestrator-night`, каждый день ~16:25 по местному времени); она находится в разделе «Сценарии» (Routines) боковой панели приложения и выполняется, только пока компьютер не в спящем режиме и подключён к сети. Процедура хранится на этом ПК (в Git и на другие ПК не переносится); на одном ПК должна быть одна такая процедура. После смены учётки Claude открыть «Сценарии» и проверить, что процедура на месте; если её нет, создать заново

## ❓ Сначала уточнить, потом делать

- Если требование можно понять двумя способами, или правка меняет вид и смысл, которые не названы прямо (что показывать, где, какими словами, каким цветом), **сначала** в 1–3 строках пересказать понимание с примером готового вида (макет строки, текст подписи) и дождаться «да»; по догадке не реализовывать
- Новые подписи и формулировки, которых пользователь не называл, показываются заранее, а не вводятся сразу в код
- Перенос элемента означает «убрать там, показать здесь»: перед правкой перечислить, что будет убрано и что добавлено
- Исключение: очевидные мелкие правки по прямому указанию (опечатка, цвет, порядок по явной просьбе)
- **Проверять перед ответом, всегда:** любое утверждение о коде, интерфейсе, данных или настройках («кнопка есть на вкладке…», «ключ задан», «сигнал пропадает») сначала проверяется по коду, базе или логам, и только потом пишется пользователю. **Записи из памяти, прошлых отчётов, переписки и справки о текущем состоянии (что включено, что загружено, какая версия, что запущено) устаревают: их нельзя пересказывать как факт, состояние сначала проверяется заново** (пример нарушения: «автосохранение отчётов выключено» из старой записи, а в базе оно включено и файлы сохраняются). Непроверенное прямо помечается словами «не проверял»; фраза «проверил только сейчас» после ответа означает нарушение правила
- **Не менять сразу то, что работает правильно, по просьбе пользователя: он может ошибаться.** Сначала проверить по коду и данным, объяснить, как это работает и почему (пример: «±» считается после закрытия интервала, поэтому в текущем интервале пусто), и только после подтверждения менять

## 🔘 Вопросы пользователю: кнопками

- Когда нужен выбор из вариантов или «да/нет», вопрос задаётся **интерактивно кнопками** (инструмент `AskUserQuestion`), а не текстовым списком в ответе: пользователь выбирает одним нажатием
- 2–4 варианта на вопрос, до 4 вопросов за раз; у каждого варианта краткое описание последствий. Рекомендуемый вариант идёт первым с пометкой «(Рекомендуется)». Вариант «Другое» добавляется автоматически
- Если выбрать можно несколько пунктов сразу, включается множественный выбор
- Открытые вопросы (нужен свой текст: имя, путь, пояснение) и сообщения «подтвердите и я продолжу» задаются обычным текстом
- Вопрос кнопками не заменяет правила «Сначала уточнить»: перед правкой всё так же показывается пересказ и пример вида; кнопки нужны для выбора
- **Не задавать вопросов о том, что ни на что не влияет** (работа системы, сервер, данные, будущие слияния): косметика вроде «Behind 1» на GitHub, порядок служебных шагов, необязательная уборка. Такое не делается и не предлагается; если позже станет важным (например, ветка отстала от `main` по файлам), сказать об этом тогда

## 🐢 Пошаговое выполнение (договорённость)

- Делать **один запрошенный шаг за раз**: изменить, пересобрать, проверить, коротко отчитаться и **ждать подтверждения** перед следующим шагом
- Не забегать вперёд: не добавлять то, о чём не просили (новые функции, данные в БД, новые таблицы, правки справки), а **предлагать** это отдельно
- Крупные задачи (дашборды, отчёты, схемы БД, фоновые сборщики данных): сначала короткий план и согласование каждого шага, потом код
- **Инструкции для программиста ПЛК (TIA Portal) и любые ручные действия пользователя даются по одному шагу.** Шаг = одно действие (создать тег, создать блок данных, изменить одну сеть). В шаге: путь в дереве проекта «как в TIA Portal» (`UBMCP_PLC` → `Program blocks` → …), что нажать или ввести, что должно получиться. Простыми словами, без длинных рассуждений. **Для каждой новой переменной, блока данных и сети сразу даётся готовый комментарий на английском языке** (текст для поля Comment, в блоке кода для копирования), чтобы в проекте TIA всё было понятно без перевода. **Когда нужно изменить существующий код (SCL, LAD), называется номер строки в редакторе TIA, текст строки «было» и текст «стало» (оба в блоках кода для копирования).** Номера строк сверяются по выгрузке с пометкой, что TIA может считать иначе (комментарии и пустые строки сдвигают нумерацию), поэтому рядом всегда пишется и сам текст строки для поиска Следующий шаг только после ответа «готово», который запрашивается **кнопками** (`AskUserQuestion`: «Готово» / «Ошибка или красный значок» / «Нужна подсказка»), а не текстом; весь план сразу не выдавать, а в начале одной строкой назвать, сколько шагов впереди
- Запись данных в БД пользователя и создание таблиц — только с явного согласия
- **Коммит и push** — только после того, как пользователь проверил результат; предложить можно, делать только по согласию
- **Ветки (работа на нескольких ПК):** у каждого разработчика своя ветка (`Taras-Ukrainets`, `Almat`, ветка серверного ПК), коммиты и push только в неё; перед каждым коммитом проверять `git branch --show-current` и не коммитить в `main`. В `main` изменения попадают только слиянием ветки (запрос на слияние на GitHub) при зелёном `pytest`; рабочий сервер обновляется только из `main` скриптом `update-server.ps1`. Правила (`CLAUDE.md`, `ORCHESTRATOR.md`) правит только владелец проекта, остальные просят; общие файлы очереди (`roadmap.md`, `done.md`) только дописываются

## 🚚 Как правки попадают на сервер (простыми словами)

1. **Правка в своей ветке.** Claude правит файлы в ветке своего ПК (на сервере это `Server`). Пока не сделан коммит, правка лежит только на этом ПК
2. **Коммит и push.** После вашей проверки Claude делает коммит (запись в историю) и push (отправка на GitHub **в свою ветку**, не в `main`). Рабочий проект при этом не меняется
3. **Тесты.** Автотесты запускаются на ПК, где есть Python и запущенная база (команда `cd tests && python -m pytest -q -n 6`: параллельно в 6 процессов, около 25 с; без `-n 6` один процесс, около 1,5 мин). На сервере Python не установлен, поэтому тесты прогоняют на ПК разработки; на сервере тоже можно: `.\run-tests.ps1` (переносные Python и node в `C:\pmm-tools`, одноразовая база в Docker на порту 5433, рабочая база не затрагивается). Все тесты должны быть зелёными
4. **Pull request (запрос на слияние).** Владелец проекта на GitHub нажимает «Compare & pull request», ветка → `main`, затем «Merge». Так проверенные правки попадают в `main`
5. **«Get» и обновление сервера.** «После слияния» значит: правки уже в `main` на GitHub. Тогда на сервере запускается `update-server.ps1`: он делает бэкап, берёт `main`, пересобирает контейнеры, проверяет и при ошибке откатывает. Claude показывает список изменений и запускает скрипт только после согласия
- Временная правка, скопированная прямо в контейнер для проверки, **пропадает** при обновлении: она живёт, только пока не закоммичена и не слита в `main`

## 🛡 Среда: разработка и рабочая (APP_ENV)

- Любая запись во внешнюю систему (ПЛК, Telegram, письма и т.п.) работает **только при `APP_ENV=prod`**; по умолчанию среда `dev`, запись запрещена, на сайте метка «Среда: разработка». На сервере создаётся файл `.env` с `APP_ENV=prod` рядом с `docker-compose.yml` (в Git не хранится)
- Единая точка записи в ПЛК: `PlcOpcClient.write_int` (поллер); новая запись в ПЛК делается только через такую же защищённую точку, и на неё пишется тест «в dev блокируется, в prod проходит»

## 🧪 Тесты

- Исправление ошибки начинается с теста, который её воспроизводит (если ошибку можно воспроизвести тестом): сначала красный тест, потом правка, потом зелёный; тест остаётся в `tests/`

## Контекст и оптимизация ответов (Context Optimization)

1. **Запрет на дублирование кода:** никогда не выводить весь файл или длинный листинг целиком, если запрошено исправление. Только изменённые фрагменты (diff, «найти и заменить» или строки с контекстом вокруг)
2. **Краткость объяснений:** без «воды», пространных введений и повторения уже известной информации. Ответы технически ёмкие и по существу
3. **Минимум лишнего текста:** на технические вопросы отвечать компактными таблицами, короткими списками и точечными фрагментами кода вместо длинных описательных абзацев
4. **Пошаговый режим:** «один шаг, один вопрос», без огромных многоблочных инструкций, которые перегружают память сессии
5. **Проверки для пользователя оформляются простым нумерованным списком** («1. где, что сделать, что должно быть»): без таблиц и без значков-чекбоксов ☐ (в чате они не нажимаются); пользователь отвечает номерами; условия (вход администратором, нужен простой на линии) отдельной строкой после списка
6. **Объяснять простыми словами:** сначала то, что пользователь увидит или получит («нажали кнопку, в архиве три файла Excel»), и только потом имена файлов, веток и скриптов; термины разработчика («выгрузка в скрипт», «worktree», «коммит») без пояснения не употреблять. Вопрос, на который ждётся ответ, ставится последней отдельной строкой
7. **Время ожидания называется заранее:** при запуске фоновой работы (воркер, сборка, прогон тестов) сразу пишется оценка «будет готово примерно в ЧЧ:ММ (≈N мин)» по времени похожих прошлых задач; если срок сдвигается, пишется новая оценка. Опыт этого проекта: небольшая правка расчёта или экрана 5–8 минут, новый экран или вкладка 8–13 минут, полный прогон тестов на сервере около 1 минуты, проверка экрана на тестовой копии 3–5 минут

## ⌨️ Команды: одна команда, один блок

- В справке и в ответах команды даются **по одной**: один блок кода (одна строка) на одну команду. Блоки из нескольких строк приводят к склейке при копировании (`git pushdocker compose stop…`), и ни одна команда не выполняется
- Несколько действий подряд выносятся в **скрипт** (например, `backup.ps1`), который запускается одной командой
- После команды, которая меняет состояние (остановка, `git push`, восстановление), указывается **проверка результата** (`docker ps`, `git status -sb`, счёт строк)
- Исключение: команда из нескольких строк допустима, только если это одна команда (например, SQL-запрос или скрипт, который нельзя сократить)
