# CLAUDE.md

**PMM (Production Monitoring & Management)**, «Мониторинг и управление производством»: опрос ПЛК, Andon/KPI, простои, отчёты, графики, тренды. Папки, контейнеры и база (`plc-monitoring-docker-poller`, `general_data_hub_BD`) не переименовываются.

## Правила по темам: прочитать перед работой
- `docs/rules-ui.md`: перед любой правкой `fastapi-api/static/` и новым элементом интерфейса
- `docs/rules-reports.md`: перед правкой расчётов, отчётов, графиков, Excel, данных из ПЛК
- `ORCHESTRATOR.md`: в режиме оркестратора

Главное из них (даже если файл не открыт):
- у нового элемента `title` 10–20 слов; цвета только зелёный, красный, синий (жёлтый нельзя); шрифты только `--fs-small/--fs-large/--fs-title`
- без наложений, шапка не ломается на 955px, после правки вёрстки `/check-layout`
- одно число везде одинаковое: считает одна функция на сервере; тайм-аут запроса 6 с; данные перечитываются сами
- Excel повторяет экран (плитки, графики, таблицы, названия, порядок), это проверяет тест
- экраны с данными работают за период: «День», «Неделя», «Месяц», «Прошлый месяц», «С»/«По», ◀ ▶
- большие таблицы как в Excel (сортировка, фильтры, копирование, `attachColWidths`)
- настройка из БД видна в интерфейсе, право проверяется на сервере; удаляет только автор и администратор, история сохраняется

## Перед началом задачи
- **Первая строка ответа: «Исход 1/2/3»**:
  1. в фоне (воркер): проверяется тестами, без решений пользователя, входа, ручной проверки
  2. в фоне при условии: назвать, что нужно от пользователя
  3. не в фоне: назвать причину (вид на устройстве, пароль, ПЛК, телевизор, подбор вёрстки по скриншотам)
  Если оркестратор делает задачу сам, сказать это и почему.
- **Сначала уточнить:** если требование понимается двояко или меняет вид и смысл, которые не названы прямо, пересказать в 1–3 строках с примером вида (макет, текст подписи) и ждать «да». Новые подписи показывать до кода. Перенос = перечислить, что убрано и что добавлено. Без уточнения только очевидные мелочи по прямому указанию.
- **Сначала вопросы, потом решение:** любая задача (вёрстка, расчёт, ПЛК, установка, настройка) начинается с вопросов кнопками (`AskUserQuestion`), по 1–2 за раз; решение, шаги и инструкции до ответов не даются. Допущения («одно расписание на все бренды?») проверяются вопросом. После ответов: пересказ в 2–3 строках с примером вида, работа после «да». Неподтверждённый вопрос из передачи задаётся первым, даже если сказано «продолжи с шага N».
- **Короткая проверка до длинного текста:** перед длинной инструкцией, кодом или планом (TIA, сайт, сервер, установка) 3 строки «что будет сделано» словами той системы (имена, типы, место); полный текст только после «да». Правка по замечанию: только изменённое, без повтора целиком.
- **Объяснение изменения:** называть блоки и переменные по именам; сначала «как работает сейчас» (по реальному коду, прочитанному до ответа), потом «что меняется» по пунктам. Без общих фраз вроде «считают по массивам».
- **Термины ПЛК не путать:** «переменная» = одно имя в блоке (`Changan_Start`), её тип может быть массивом (`Array[1..13] of DInt`); «элемент» = одно значение внутри (`Changan_Start[5]`); «блок» = DB, FB, FC. Слова «таблица», «строка» для ПЛК не употреблять. Всегда писать имя и тип целиком, а передачу массива в вызов отличать от обращения к элементу.
- **Проверять перед ответом:** любое утверждение о коде, данных, настройках, состоянии проверять по коду, БД, логам сейчас. Память, прошлые отчёты и справка устаревают. Непроверенное помечать «не проверял».
- **Не менять работающее по просьбе сразу:** сначала проверить и объяснить, как это работает; менять после подтверждения.

## Пошаговый режим (по умолчанию)
- Один запрошенный шаг: изменить, пересобрать, проверить в браузере, коротко отчитаться, ждать подтверждения
- Не добавлять то, о чём не просили (функции, данные в БД, таблицы, справку): предлагать отдельно
- Крупные задачи (дашборды, отчёты, схемы БД, сборщики): сначала короткий план, согласовать каждый шаг
- Запись в БД пользователя и новые таблицы только с явного согласия
- Commit и push только после проверки пользователем, один проверенный шаг = один commit

## Инструкции для TIA Portal и ручные действия пользователя
- По одному действию за шаг; в начале одной строкой сколько шагов впереди- Путь как в дереве TIA (`UBMCP_PLC` → `Program blocks` → …), что нажать или ввести, что должно получиться
- Для каждой новой переменной, DB и сети готовый комментарий **на английском** в блоке кода
- Правка кода (SCL, LAD): номер строки (с оговоркой, что TIA может считать иначе) + текст «было» и «стало», оба в блоках кода
- Следующий шаг после ответа кнопками: «Готово» / «Ошибка или красный значок» / «Нужна подсказка»

## Вопросы пользователю
- Выбор и «да/нет» только кнопками (`AskUserQuestion`), рекомендуемый вариант первым с «(Рекомендуется)»; пользователь отвечает с телефона, а вопрос в поле «следующий шаг» (wrap_up) там не виден, поэтому вопрос с выбором всегда через `AskUserQuestion`
- Открытые вопросы (имя, путь, пояснение) обычным текстом, последней строкой
- Не спрашивать о том, что ни на что не влияет (косметика GitHub, порядок служебных шагов, необязательная уборка)

## Ответы
- Простыми словами: сначала что пользователь увидит, потом имена файлов и веток; термины («коммит», «worktree») с пояснением
- Кратко: таблицы и списки, только изменённые фрагменты кода, без пересказа известного
- Проверки для пользователя простым нумерованным списком без ☐; условия (вход админом, простой линии) отдельной строкой
- Команды по одной в блоке; несколько действий в скрипт (`.ps1`); после команды, меняющей состояние, команда проверки
- При фоновой работе сразу «готово примерно в ЧЧ:ММ (≈N мин)», время по часам ПК (`Get-Date`); ориентиры: правка расчёта/экрана 5–8 мин, новый экран 8–13, тесты на сервере ~1, проверка экрана на копии 3–5
- 💡 Совет (не больше 1–2 за ответ, одной строкой: что, зачем, сколько работы), если видно готовое решение лучше (Siemens/TIA, стандарт, библиотека, GitHub). Проверять по источнику, у проектов лицензия, активность, звёзды. Данные завода наружу не отправлять

## Ветки и выпуск
- У каждого разработчика своя ветка (`Taras-Ukrainets`, `Almat`, серверная `Server*`); перед коммитом `git branch --show-current`, в `main` не коммитить
- В `main` только слиянием на GitHub при зелёном `pytest`; рабочий сервер обновляется только из `main` скриптом `update-server.ps1`, запуск после согласия
- Тесты: `cd tests && python -m pytest -q -n 6` (~25 с); на сервере `.\run-tests.ps1` (одноразовая база на 5433, рабочая не затрагивается)
- Исправление ошибки начинается с красного теста, который её воспроизводит; тест остаётся в `tests/`
- `CLAUDE.md` и `ORCHESTRATOR.md` правит только владелец; `roadmap.md`, `done.md` только дописываются
- Как это выглядит для человека, простыми словами: `docs/release.md`

## Среда (APP_ENV)
- Запись во внешние системы (ПЛК, Telegram, письма) только при `APP_ENV=prod` (`.env` на сервере, не в Git); по умолчанию `dev`, запись запрещена
- Запись в ПЛК только через `PlcOpcClient.write_int` или такую же защищённую точку, с тестом «в dev блокируется, в prod проходит»

## Режим оркестратора
- Когда пользователь не может следить; правила в `ORCHESTRATOR.md`. Запуск по процедуре `orchestrator-night` или фразой «режим оркестратора»
- Очередь только своего ПК `tasks/queue-<имя>.md`; идеи `tasks/roadmap.md`, закрытое `tasks/done.md`, обзор практик `tasks/ideas.md`
- Без commit и push; задачи с решением пользователя (данные в БД, расписание Windows, схемы, перенос на сервер) помечаются `[!]` и не выполняются
- Вёрстка в фоне: воркеры правят CSS/JS без браузера, затем один проверочный воркер пересобирает контейнер и проверяет `/check-layout` (браузер и контейнер общие, параллельно нельзя). Экраны администратора, телевизор, устройства: исход 3
