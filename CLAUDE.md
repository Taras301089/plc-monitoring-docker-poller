# CLAUDE.md — Инструкции для Claude Code

Система называется **PMM (Production Monitoring & Management)**, по-русски «Мониторинг и управление производством»: опрос ПЛК, доска Andon/KPI, простои, отчёты, графики, тренды. Названия папок, контейнеров и базы (`plc-monitoring-docker-poller`, `general_data_hub_BD`) не переименовываются.

## 📋 Управление задачами

**Когда даете список задач:**
- Структурируйте задачи нумерованным списком в одном сообщении
- Я буду выполнять по одной и отслеживать статус
- После выполнения каждой задачи отчитываюсь и жду вашей проверки; commit делаю только после подтверждения (см. раздел «Пошаговое выполнение»)
- В конце покажу чеклист всех выполненных работ

**Пример:**
```
Задачи:
1. [ ] Убрать id из селектора, показать IP и статус
2. [ ] Перевести интерфейс на русский
3. [ ] Переименовать табы навигации
4. [ ] Добавить индикатор подключения
```

**Приоритеты:**
- Первый запрос: обновляю/добавляю этот раздел в MD
- Каждая проверенная и подтверждённая задача: один commit (после вашего согласия)
- Тестирование: после каждого изменения загружаю в браузер и проверяю

## 🔀 Режимы работы

1. **Пошаговый (по умолчанию):** пользователь за ПК, действуют правила раздела ниже
2. **Оркестратор и воркеры:** пользователь на работе и не может следить; правила в `ORCHESTRATOR.md`, очередь задач в `tasks/queue.md`. Запускается автоматически **в 16:25** (рабочие дни, время ПК; плановая задача `orchestrator-night`), если в очереди есть невыполненные задачи; фразой «режим оркестратора» можно запустить вручную. Коммит и push в этом режиме не делаются: результат ждёт проверки пользователя. Задачи, где нужно решение пользователя (данные в БД, расписание Windows, схемы, перенос на сервер), помечаются `[!]` и не выполняются
- **Для каждой новой задачи сначала определяется, можно ли делать её в фоне** (воркером), и пользователю сообщается один из трёх исходов:
  1. **Можно в фоне:** задача проверяется тестами, не требует решений пользователя, входа или ручной проверки; запускается воркер, результат принимает оркестратор по тестам
  2. **В фоне можно, если будет выполнено условие:** называется, что нужно от пользователя (решение, согласие на схему БД или правку поллера, вход администратором, доступ, уточнение вида), и после этого задача запускается
  3. **В фоне не получится:** называется причина (например, нужна визуальная проверка на устройстве, ввод пароля, физический доступ к ПЛК или телевизору, правка вёрстки с подбором по скриншотам); задача выполняется вместе с пользователем в обычном режиме
- Правка вёрстки: воркер может править CSS и JS, но проверить вид (наложения, размеры) может только оркестратор через встроенный браузер; поэтому такие задачи идут «в фоне» только в паре «воркер правит, оркестратор проверяет»
- Автозапуск настроен как плановая задача `orchestrator-night` (Пн–Пт, 16:25 по местному времени); управляется в разделе «Запланированные» боковой панели приложения, срабатывает только при открытом приложении и включённом ПК

## ❓ Сначала уточнить, потом делать

- Если требование можно понять двумя способами, или правка меняет вид и смысл, которые не названы прямо (что показывать, где, какими словами, каким цветом), **сначала** в 1–3 строках пересказать понимание с примером готового вида (макет строки, текст подписи) и дождаться «да»; по догадке не реализовывать
- Новые подписи и формулировки, которых пользователь не называл, показываются заранее, а не вводятся сразу в код
- Перенос элемента означает «убрать там, показать здесь»: перед правкой перечислить, что будет убрано и что добавлено
- Исключение: очевидные мелкие правки по прямому указанию (опечатка, цвет, порядок по явной просьбе)
- **Не менять сразу то, что работает правильно, по просьбе пользователя: он может ошибаться.** Сначала проверить по коду и данным, объяснить, как это работает и почему (пример: «±» считается после закрытия интервала, поэтому в текущем интервале пусто), и только после подтверждения менять

## 🐢 Пошаговое выполнение (договорённость)

- Делать **один запрошенный шаг за раз**: изменить, пересобрать, проверить, коротко отчитаться и **ждать подтверждения** перед следующим шагом
- Не забегать вперёд: не добавлять то, о чём не просили (новые функции, данные в БД, новые таблицы, правки справки), а **предлагать** это отдельно
- Крупные задачи (дашборды, отчёты, схемы БД, фоновые сборщики данных): сначала короткий план и согласование каждого шага, потом код
- Запись данных в БД пользователя и создание таблиц — только с явного согласия
- **Коммит и push** — только после того, как пользователь проверил результат; предложить можно, делать только по согласию

## 🛡 Среда: разработка и рабочая (APP_ENV)

- Любая запись во внешнюю систему (ПЛК, Telegram, письма и т.п.) работает **только при `APP_ENV=prod`**; по умолчанию среда `dev`, запись запрещена, на сайте метка «Среда: разработка». На сервере создаётся файл `.env` с `APP_ENV=prod` рядом с `docker-compose.yml` (в Git не хранится)
- Единая точка записи в ПЛК: `PlcOpcClient.write_int` (поллер); новая запись в ПЛК делается только через такую же защищённую точку, и на неё пишется тест «в dev блокируется, в prod проходит»

## 🧪 Тесты

- Исправление ошибки начинается с теста, который её воспроизводит (если ошибку можно воспроизвести тестом): сначала красный тест, потом правка, потом зелёный; тест остаётся в `tests/`

## ⚙️ Настройки видны в интерфейсе

## 💡 Всплывающие подсказки (Tooltips)

**Правило для всех новых элементов:**
- Каждая кнопка, поле ввода, иконка должны иметь `title` атрибут
- Описание должно быть развёрнутым (10-20 слов), объяснять ЗАЧЕМ и ЧТО делает элемент
- Формат: `title="Что делает элемент и как его использовать"`
- Примеры:
  - ✅ `title="Обновить переменные с ПЛК (сканирование OPC UA, может занять время)"`
  - ❌ `title="Обновить"` (слишком короткое)

**Для интерактивных элементов:**
- Кнопки → объясняем действие
- Иконки → объясняем статус (🟢 = на связи, ❌ = отключено)
- Чекбоксы → объясняем опцию (например, "Архив", "Grafana", "Авария")
- Фильтры → объясняем синтаксис поиска

## 📑 Таблицы работают как в Excel

Пользователи привыкли к Excel, поэтому в больших таблицах **максимально использовать его функции и лучшие практики**:
- **Сортировка** по любому столбцу кликом по заголовку (по возрастанию, по убыванию, сброс), с индикатором стрелкой; Shift+клик добавляет второй уровень сортировки
- **Фильтры в заголовках** столбцов: список значений с чекбоксами и поиском, отметка столбцов с активным фильтром, кнопка «Сбросить фильтры»
- **Выделение и копирование**: выделение ячейки, диапазона (мышью или Shift+клик), столбца (Ctrl+клик по заголовку), всей таблицы (Ctrl+A); Ctrl+C копирует в буфер как текст с табуляцией, чтобы вставлялось в Excel; кнопка «Копировать таблицу»
- В каждой строке **все ячейки заполнены** (без «объединённых» пустых ячеек), чтобы сортировка, фильтры и копирование не теряли данные; повторяющиеся значения можно лишь приглушить цветом. **Исключение: числа, которые суммируют** (план, факт, минуты интервала при нескольких строках на один интервал): они записываются один раз, на первой строке группы, иначе сумма столбца в Excel завышается. Внизу таблицы строка «Итого» с формулами `SUM`, значения в ней должны совпадать с плитками на экране
- Порядок столбцов от общего к частному (например, Бренд, Участок, Станция); числа выровнять, у каждого заголовка `title`
- **Ширина столбцов меняется перетаскиванием границы в заголовке (как в Excel) во всех больших таблицах** (Andon, Простои, Пользователи, Справочники и новые): подключать `window.attachColWidths(table, "ключ")` из `colwidths.js` после каждой отрисовки таблицы; ширины хранятся на сервере (личные у вошедшего пользователя; администратор с Shift при отпускании сохраняет общие для всех и для табло), двойной щелчок по границе возвращает по умолчанию, у ручки есть `title`
- Позже: выгрузка в Excel (.xlsx), закрепление шапки при прокрутке

## 🚫 Не дублировать надписи

- Заголовок внутри вкладки **не повторяет название самой вкладки** (во вкладке «Простои» нет заголовка «Простои», в «Пользователи» нет «Пользователи»): название уже видно в панели навигации
- Одно и то же не писать дважды на экране: в заголовке и подзаголовке, в подписи и рядом в подсказке-тексте
- Достаточно короткого описания (что здесь можно сделать) и самих элементов; подробности уходят в `title`
- **Один факт не показывается дважды в одном элементе:** цвет, значок или точка уже говорят о состоянии, поэтому текст рядом не повторяет его словами (пример: зелёная точка у ПЛК уже значит «связь есть», справа пишется только когда было последнее обновление с ПЛК, без слов «опрос»/«связь есть»; у красной точки справа время и причина, без слов «нет связи»)

## 📊 Best Practices для больших списков (50+ элементов)

**Минимальный набор функций:**

### ✅ Нумерация
- Используй порядковые номера (1., 2., 3., ...) перед элементами
- Помогает быстро ориентироваться и ссылаться на конкретный элемент
- Визуально похоже на Excel/Google Sheets - привычный формат для пользователей
- Особенно важно, когда элементы содержат длинные имена (обрезаются на экране)
- **Опционально:** кнопка показать/скрыть номера (№) для минималистичного вида
- Пример: `1. ClampSignal_MB060_FIX07_R_V44 (18 переменных)`

### 🔍 Поиск (фильтр)
- Обязательно добавь поле быстрого поиска для фильтрации по названию
- Поиск должен быть case-insensitive (игнорировать регистр)
- Работать в реальном времени (по мере ввода)
- Реагировать на Enter для явного применения фильтра
- Пример: `Поиск по блокам` → фильтрует Data Blocks по названию

### ↕️ Сортировка
- Добавь минимум 2 кнопки: сортировка A-Я и Я-А
- Кнопка активного порядка должна быть выделена цветом
- Сортировка должна применяться к уже отфильтрованным результатам
- Сохраняй выбор сортировки в session (пока страница открыта)
- Пример: `▲ А-Я` и `▼ Я-А` кнопки в контрольной панели списка

### 📈 Дополнительные рекомендации
- **Счётчик результатов:** если нужно, покажи сколько элементов найдено после фильтра
- **Группировка:** для очень больших списков (500+) добавь группировку по первым буквам
- **Скролл:** при клике на элемент сохрани позицию скролла для быстрого возврата
- **Сохранение состояния:** помни состояние сортировки и поиска при переключении ПЛК
- **Доступность:** убедись что кнопки управления легко нажимать (мин. 32x32px)
- **Эффективность:** используй debounce/throttle для поиска при очень больших списках

## 📐 Адаптивная вёрстка (разные экраны и устройства)

Сайт открывают на мониторе, ноутбуке с масштабом Windows 125–150%, в окне на пол-экрана и на телевизоре, поэтому:
- **Никаких наложений:** нельзя ставить блоки поверх контента через `position: absolute/fixed`, если их ширина может расти (группы кнопок, плитки, индикаторы). Блок, которому не хватает места, переносится на новую строку или уходит под соседа (flex-wrap, grid), а не залезает на соседа
- **Новая кнопка или плитка в шапке** = проверка, что шапка не ломается при ширине 955px; если не помещается, правило для узкого окна (`@media (max-width: ...)`) добавляется сразу
- **Размеры шрифтов таблицы задаются одним общим правилом** (`clamp()` от высоты и ширины окна), а не отдельным размером для каждой колонки; заголовки колонок тоже масштабируются по ширине
- **Новые стили и скрипты** подключаются через главную страницу: адреса получают версию автоматически (`?v=`), старый кэш на ноутбуках и телевизорах не держится
- **После любой правки вёрстки** запускать проверку `/check-layout`: она открывает страницу в типичных размерах, ищет наложения и обрезанный текст и присылает скриншоты. Финально проверяют на реальных устройствах (ноутбук пользователя, телевизор)

## 🔤 Шрифты и размеры (единый вид по всему сайту)

- **Шрифтов (семейств) на всём сайте не больше двух:** `Segoe UI` (с запасными Roboto, Arial) для текста и цифр. Второй при необходимости только для кода или имён переменных ПЛК. Цифры таблиц в том же шрифте с `font-variant-numeric: tabular-nums`, без отдельного моноширинного шрифта и перечёркнутых нулей
- **Размеров шрифта на одном экране не больше трёх:** мелкий (подписи, заголовки колонок, причины, кнопки, подсказки), крупный (числа и время в таблицах Andon, значения в плитках) и заголовочный (название бренда, такт-тайм, часы). Одинаковые элементы всегда одного размера; разовые размеры «для одной колонки» не вводить
- **Размеры одни и те же на всех экранах сайта:** значения задаются переменными в `:root` (`--fs-small`, `--fs-large`, `--fs-title`), а не числами в каждом правиле. Новый элемент берёт размер из этих переменных
- Подсказки и мелкие служебные подписи (tooltips, номера строк) в счёт не идут, но тоже берутся из переменных
- На обычных экранах значения такие: мелкий 13px, крупный 16px, заголовочный 22px. На Andon своя шкала под телевизор (плавающие размеры в `#andon`, в режиме табло мелкий крупнее). Панель навигации сверху и значок темы это общий каркас, в счёт размеров экрана не входят (мелкий 13px)

## 🎨 Цвета (не более трёх акцентных)

- Акцентных цветов на экране три: **зелёный, красный, синий**. Всё остальное нейтральное (белый, оттенки серого, фоны)
- Значения: зелёный = норма и факт (`--ok`); красный = проблема, простой, отставание (`--danger`); синий = действия и выбранное: активная вкладка, фокус, ссылки, главная кнопка (`--accent`)
- Жёлтый и оранжевый (`--warn`) не использовать: перерыв, обед, пауза показываются нейтральным серым с подписью
- Цветом выделяются значения и состояния, а не обычный текст: основной текст белый, второстепенный серый
- Оттенки одного цвета (бледная подложка, мягкий красный) допустимы и не считаются новым цветом
- Правило относится к цвету текста, подсветок, рамок и фонов
- **Цветная точка у ПЛК означает только наличие связи** (последний опрос успешен: зелёная; нет связи: красная). Флаг «Включён в опрос» точкой не показывается: выключенный ПЛК виден приглушённой строкой и чекбоксом в окне редактирования

## 📅 Период везде (единый выбор даты)

Любой экран с данными за время (Графики, Отчёты, Простои, статистика пользователей и новые) работает **за период**, а не за один день:
- **Быстрые кнопки одинаково называются и считаются везде:** «День» (сегодня), «Неделя» (последние 7 дней), «Месяц» (с первого числа по сегодня), «Прошлый месяц», и поля **«С» / «По»** для любого периода. Активный вариант подсвечен
- Кнопки **◀ ▶** сдвигают выбранный период на его длину; дата не позже сегодняшней
- Если выбран один день, показываются данные по часам, если несколько дней, показываются итоги по дням и сводные таблицы
- **Выгрузка в Excel** всегда за выбранный период (один день даёт таблицу дня, период даёт сводный отчёт с графиками), выбор линии и периода запоминается
- Даты и «сегодня» берутся из времени сервера (`plantClock`), а не из часов браузера

## 📥 Имена скачиваемых файлов

Файл называется по экрану, **откуда его скачали**, затем участок и период: `<Экран>_<участок>_<период>.xlsx`.
- Вкладка «Отчёты»: `Отчёты_GWM_2026-10-05.xlsx` (день), `Отчёты_GWM_2026-10-01_2026-10-06.xlsx` (период)
- Вкладка «Графики»: `Графики_GWM_2026-10-01_2026-10-06.xlsx`; график отдельно: `Графики_GWM_план-факт_2026-10-01_2026-10-06.xlsx`
- Экран Andon (кнопка «Excel»): `Andon_GWM_2026-10-05.xlsx`
- Вкладка «Простои» и новые: то же правило (в `SRC_NAMES` в `history.py` добавляется название экрана, клиент передаёт `src=` в адресе выгрузки)
- Файлы автосохранения в папке: `Отчёт_<участок>_<день>.xlsx` и `Отчёт_<участок>_месяц_<ГГГГ-ММ>.xlsx`
- Название файла не должно совпадать с названием другого экрана; участок без «Main Line» (GWM, Chery, FL_RB262), дата в формате ГГГГ-ММ-ДД

## 📤 Excel-отчёты выглядят как веб-экран

Выгружаемый отчёт повторяет то, что пользователь видит на экране, и в том же порядке, а не «сырые данные на отдельных листах»:
- **Порядок на листе сверху вниз:** заголовок (линия и период), **плитки итогов**, **график**, **таблицы** (у каждой названием служит заголовок как на экране: «По дням», «Причины простоя», «Простой по станциям», «Таблица отчёта»). Дополнительные диаграммы стоят справа от своей таблицы
- **Основной отчёт на одном листе** (день: «День»; период: «Отчёт»). Дополнительные листы только для данных, которых нет на экране (полный список простоев) или для служебных данных графика (скрытый лист «График»); вторую вкладку, дублирующую первую, не делать
- **Всё, что есть на экране, есть в файле**, и числа совпадают с плитками; названия колонок и подписи те же, что в вебе
- **Вид тоже общий:** те же названия, цвета значений (зелёный факт, красный простой), форматы чисел и процентов, выравнивание; плитки оформляются ячейками с рамкой как на экране
- Меняется экран (новая плитка, колонка, график), то же самое вносится в Excel, и наоборот
- **Состав экрана и файла совпадает полностью:** каждая плитка, каждый график и каждая таблица экрана есть в файле, в том же порядке, с теми же названиями, подписями легенды и цветами рядов (план серый, факт синий, % выполнения зелёная линия, простой красный). Новый график или плитка на экране появляется в Excel в той же задаче, иначе задача не закончена (пример нарушения: график «Накопленное производство за день» есть на вкладке «Графики», а в файле «Отчёт за период» его нет)
- **Соответствие проверяется тестом:** для каждого экрана с выгрузкой в `tests/` есть проверка, что список плиток и графиков в `.xlsx` (названия графиков в `xl/charts`) совпадает со списком на экране; при добавлении элемента на экран тест обязан упасть, пока его нет в файле
- Перед сдачей файл открывается и сравнивается с экраном по списку проверок (плитки, графики, таблицы, названия, цвета)
- Правила про итоги (`SUM`, значения интервала один раз на группу строк) и имена файлов (раздел ниже) сохраняются

## Контекст и оптимизация ответов (Context Optimization)

1. **Запрет на дублирование кода:** никогда не выводить весь файл или длинный листинг целиком, если запрошено исправление. Только изменённые фрагменты (diff, «найти и заменить» или строки с контекстом вокруг)
2. **Краткость объяснений:** без «воды», пространных введений и повторения уже известной информации. Ответы технически ёмкие и по существу
3. **Минимум лишнего текста:** на технические вопросы отвечать компактными таблицами, короткими списками и точечными фрагментами кода вместо длинных описательных абзацев
4. **Пошаговый режим:** «один шаг, один вопрос», без огромных многоблочных инструкций, которые перегружают память сессии
5. **Проверки для пользователя оформляются простым нумерованным списком** («1. где, что сделать, что должно быть»): без таблиц и без значков-чекбоксов ☐ (в чате они не нажимаются); пользователь отвечает номерами; условия (вход администратором, нужен простой на линии) отдельной строкой после списка

## 🔒 Идентичность данных (одно число везде одинаковое)

Одно и то же число (план, факт, простой, такт-тайм) должно совпадать на телевизоре, ПК, в «Отчётах», «Графиках» и в Excel:
1. **Один источник правды:** у каждого числа один источник (ПЛК или одна таблица БД). Копии (кэш браузера, снимки, отчёты) только читают его и не считают по-своему
2. **Одна функция расчёта:** итоги плана, простоя и «не описано» считает одна общая функция на сервере; экраны, графики, отчёты и Excel вызывают её, а не пересчитывают сами
3. **Никакого «загрузил один раз»:** всё, что может измениться с другого устройства (план и расписание, простои, справочники), экран перечитывает сам: на табло не реже чем раз в 5 секунд, на остальных вкладках при каждом открытии и по таймеру. Данные, загруженные при открытии страницы и больше не обновляемые, считаются ошибкой
4. **Тайм-аут на каждый запрос** (не более 6 секунд): зависший запрос не должен останавливать обновление экрана
5. **Нет связи, нет цифр:** после двух неудачных опросов подряд числа из ПЛК показываются как «—» (прочерк, как «нет значения»), значок красный «● нет связи»; устаревшие цифры под значком LIVE показывать нельзя. Строки таблицы остаются на месте, чтобы вёрстка не прыгала; при восстановлении связи числа возвращаются сразу
6. **Изменил здесь, увидел везде:** любая правка (план, простой, комментарий) через ≤10 секунд даёт то же число на ПК, телевизоре, в «Отчётах», «Графиках» и в Excel; это проверяется на втором устройстве или в двух окнах
7. **Сверка перед сдачей:** план, факт и простой за выбранный день сравниваются по четырём местам (Andon, Отчёты, Графики, Excel); расхождение означает, что задача не закончена
8. **Запись с подтверждением чтением** (записали и перечитали из ПЛК) и журнал «кто, когда, было, стало»

## ✍️ Единый порядок «содержание, затем автор»

Везде, где рядом показаны текст и его автор (причина простоя, комментарий, примечание, строка отчёта и Excel):
- **Сначала содержание, затем автор** мелким серым в конце: `текст · Фамилия, должность`
- Автор записывается как **«Фамилия, должность»** (должность по роли: Мастер, Начальник участка и т.д.), без префиксов «Внёс:» на экране Andon
- Пример: `UB-20 · Оборудование. Работа ОТО · Исимов, Начальник участка`, затем `сломал датчик · Иванов, Мастер` (комментарий выглядит как продолжение описания простоя, без значка пузыря: это то же описание, только от другого отдела)
- Порядок «автор: текст» не использовать; в подсказке автор в скобках после текста
- **Комментарий начинается с разделителя «↳»** (серый): так видно, что это ответ или дополнение к описанию выше, а не новая причина; значок пузыря не используется
- Число видимых строк в ячейке «Причина» считается **по видимым интервалам** (скрытые неактивные интервалы не учитываются), иначе строки комментариев пропадают

## 🗑 Удаление записей

- **Удаляет только автор записи и администратор** (описание простоя, комментарий и любые похожие записи); начальники и остальные чужое не удаляют. Правило проверяется на сервере, а не только скрытием кнопки
- **Кнопка называется «Удалить»** (текстом), а не крестиком «✕»: действие должно быть понятно без догадок
- **История сохраняется в базе:** удаление не стирает данные. Комментарии помечаются `deleted_at`; удалённые строки описания копируются в журнал `kpi_downtime_items_log` (что было, кто создал, кто и когда удалил). Новые удаляемые сущности делаются по тому же принципу

## 📐 Колонка «Причина» использует всю ширину

- Каждая причина простоя выводится **своей колонкой** (причина, описание, комментарий; колонки идут слева направо), «не описано N мин» отдельной колонкой в конце. Скрывать причину нужно, только если она реально не помещается по ширине ячейки; тогда показывается «+N»
- Нельзя скрывать текст «по привычной норме строк», пока справа есть свободное место

## ⌨️ Команды: одна команда, один блок

- В справке и в ответах команды даются **по одной**: один блок кода (одна строка) на одну команду. Блоки из нескольких строк приводят к склейке при копировании (`git pushdocker compose stop…`), и ни одна команда не выполняется
- Несколько действий подряд выносятся в **скрипт** (например, `backup.ps1`), который запускается одной командой
- После команды, которая меняет состояние (остановка, `git push`, восстановление), указывается **проверка результата** (`docker ps`, `git status -sb`, счёт строк)
- Исключение: команда из нескольких строк допустима, только если это одна команда (например, SQL-запрос или скрипт, который нельзя сократить)
