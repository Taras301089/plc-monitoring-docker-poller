📊 Архитектура проекта

Дни без выпуска и «Простой весь день (поломка линии)»

Если за закрытый день (раньше сегодняшнего по времени сервера) на линии не произведено ни одного кузова, это выходной или нет плана: автоматический простой и «не описано» за этот день не считаются нигде (Andon и его архив, «Простои», «Графики», «Отчёты», Excel, автосохранение). Строка дня остаётся в таблице «По дням» (план и факт 0, строка выделена), но в план, факт, % выполнения и «Дней с данными» периода и на график план-факт такой день не входит; «±» не показывается, вместо простоя подпись «нет выпуска». Текущий день правило не применяет. Простои, которые люди уже описали, остаются и считаются. Правило одно на сервере (dayflags.py), экраны только читают его результат. У подсборок (ручной ввод) правило действует, когда по интервалам введены факты и их сумма равна нулю.

Если линия в такой день стояла из-за поломки, во вкладке «Отчёты» (один день, одна линия) нажмите «Простой весь день (поломка линии)»: время простоя дня пойдёт в статистику как у рабочего дня. Кнопка видна только для закрытого дня без выпуска и только тем, кто может править (кроме роли «Просмотр»); поставить отметку можно только для такого дня, иначе сервер ответит 409. Снять отметку может автор и администратор. Каждое изменение пишется в журнал kpi_day_flags_log (кто, когда, было, стало); таблицы kpi_day_flags и журнал создаются при старте API сами. Изменение видно на всех экранах не позднее чем через 5–10 секунд.

Среда: разработка и рабочая (APP_ENV)

Запись в ПЛК (сейчас это «план на день» на экранах Finish Line) разрешена только в рабочей среде. Переменная APP_ENV по умолчанию dev (запись запрещена, в шапке сайта метка «Среда: разработка»). На сервере в папке проекта рядом с docker-compose.yml нужно создать файл .env со строкой APP_ENV=prod (в Git он не попадает) и пересоздать контейнеры. Если файл забыт, запись плана FL не пройдёт с сообщением «Режим разработки: запись в ПЛК отключена», сами ПЛК не пострадают.

Обновление сервера одной командой

Нажмите «Скопировать», откройте PowerShell на сервере (Пуск, набрать PowerShell, от имени администратора), вставьте команду правой кнопкой мыши или Ctrl+V и нажмите Enter. Команды выполняйте по одной.

Первый раз (когда файла update-server.ps1 на сервере ещё нет): сначала вручную git pull в папке проекта, затем запустите скрипт с ключом -Force (он пересоберёт образы, даже если версия уже последняя). Дальше обычный запуск без ключей.

Первый раз, шаг 1: перейти в папку проекта, затем получить новую версию (две отдельные команды, по одной):

cd C:\plc-monitoring-docker-poller
git pull

Первый раз, шаг 2: запуск с ключом -Force:

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\update-server.ps1 -Force

Скрипт update-server.ps1 в корне проекта обновляет рабочий сервер без ручных шагов. По порядку: проверяет окружение (git, docker, папка проекта); запоминает текущий коммит; всегда делает бэкап (backup.ps1, без свежего успешного бэкапа обновление не начинается); останавливается, если изменены отслеживаемые файлы (кроме n8n_data и grafana_data); получает новую версию через git pull --ff-only (если версия уже последняя, пересборки нет); создаёт или правит .env со строкой APP_ENV=prod; пересобирает образы fastapi-api и plc-monitoring-docker-poller; запускает их (база и остальные сервисы не пересоздаются); до 90 секунд проверяет, что контейнеры работают, /api/env отвечает prod, а /api/plcs отдаёт список ПЛК.

Запуск (одна команда):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\update-server.ps1

Проверка результата: в конце окна написано «Обновление завершено успешно» и показаны прежний и новый коммит. Контейнеры можно проверить командой:

docker ps

Пробный запуск без изменений (только печатает, что было бы сделано):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\update-server.ps1 -DryRun

Ярлык на рабочем столе сервера (одна команда в PowerShell):

$s = (New-Object -ComObject WScript.Shell).CreateShortcut("$env:USERPROFILE\Desktop\Обновить PMM.lnk"); $s.TargetPath = "powershell.exe"; $s.Arguments = '-NoProfile -ExecutionPolicy Bypass -File "C:\plc-monitoring-docker-poller\update-server.ps1"'; $s.WorkingDirectory = "C:\plc-monitoring-docker-poller"; $s.Save()

Проверка: на рабочем столе появился ярлык «Обновить PMM»; окно после запуска не закрывается, пока не нажать Enter.

Откат. Если сборка, запуск или итоговая проверка не прошли, скрипт сам возвращает прежний коммит (git reset --keep, живые файлы n8n_data не затираются), заново собирает и запускает прежнюю версию и пишет «ОТКАТ ВЫПОЛНЕН: работает прежняя версия …» или «ОТКАТ НЕ УДАЛСЯ: нужна ручная проверка» с командами диагностики. Если не прошли шаги до получения новой версии, ничего не менялось, откат не нужен. Журнал каждого запуска сохраняется в C:\plc-backups\update-logs.

Копирование отчётов в сетевую папку

Скрипт copy-reports.ps1 в корне проекта копирует новые и изменённые файлы *.xlsx из локальной папки отчётов (C:\Andon-Reports, вместе с подпапками «год-месяц» и линий) в сетевую папку через robocopy. Структура подпапок сохраняется, в сетевой папке ничего не удаляется. Журнал пишется в C:\plc-backups\update-logs\copy-reports-ГГГГ-ММ-ДД.log. Код выхода 0 означает успех, 1 означает ошибку (сетевая папка недоступна или robocopy вернул 8 и больше). Сетевую папку в контейнер не подключаем: копирует хост.

Пробный запуск (ничего не копирует, только проверяет, что обе папки доступны):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\copy-reports.ps1 -DryRun -NoPause

Ежедневная задача планировщика на сервере (одна команда в PowerShell от имени администратора). Задача должна идти под учётной записью, у которой есть доступ к сетевой папке: запускайте команду под ней, без параметра /RU SYSTEM (учётная запись SYSTEM к сетевой папке доступа обычно не имеет):

schtasks /Create /SC DAILY /ST 23:50 /TN "PMM copy reports" /TR "powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\copy-reports.ps1 -NoPause"

Проверка: задача есть в списке, у неё указано время следующего запуска.

schtasks /Query /TN "PMM copy reports"

Время 23:50 выбрано позже автосохранения отчётов (оно идёт в заданное для линии время в экране «Отчёты»), чтобы в сетевую папку попал уже готовый файл дня. Автосохранение пишет один файл в день на линию с одним листом «Отчёт»: сверху отчёт дня, ниже отчёт с начала месяца по этот день.

Выгрузка проектов TIA Portal в XML

Во вкладке «ПЛК» в строке выбора ПЛК, рядом с «⟳ Обновить с ПЛК», есть кнопка «🧩 Выгрузить проект TIA» (видна только администратору). Она открывает окно «Выгрузка проекта TIA», которое выгружает проект TIA Portal в XML и Excel; сам проект не меняется и не сохраняется. Окно закрывается кнопкой «Закрыть», клавишей Esc или щелчком вне окна; начатая выгрузка при этом продолжается. Пока окно открыто или идёт выгрузка, состояние перечитывается каждые 4 секунды. В окне:

  • ПЛК: все ПЛК системы; у кого уже есть пара «ПЛК → проект», к названию добавлено «— проект: <папка>». При открытии окна выбран ПЛК, выбранный вверху вкладки; дальше выбор в окне от верхнего списка не зависит
  • Проект (папка): файлы .ap17, которые служба выгрузки нашла в разрешённых папках («GWM\UB\UB.ap17 — изменён 20.10 12:03»). У ПЛК с парой список стоит на её проекте. Перед запуском под списком строка «ПЛК GWM_UB ↔ проект GWM\UB\UB.ap17». Выгрузка запоминает эту пару: прежний путь проекта уходит в историю записи (до 5). Если проектов нет, подпись «служба выгрузки не нашла проекты в разрешённых папках» подсказывает, где задать папки поиска
  • Путь сохранения: папка для копии ZIP, по умолчанию последний путь этого проекта или C:\tia-bridge\out. Допустим полный путь с буквой диска (D:\TIA\Выгрузки) или сетевой (\\сервер\папка), не длиннее 240 знаков, без «..»; корень диска, системные папки (Windows, Program Files, ProgramData) и корень профиля (C:\Users\имя) запрещены. Путь проверяет сайт и ещё раз служба: она создаёт папку и пробует записать в неё файл; если нельзя, заявка сразу получает ошибку «Папка недоступна для записи», TIA не запускается
  • Выгрузить: ставит заявку; кнопка неактивна, пока служба не запущена, не выбраны ПЛК и проект или выгрузка уже идёт. Рядом индикатор «● служба работает» / «● служба не запущена»
  • Ниже состояние выбранного ПЛК: «в очереди», «выгружается…», «готово» или «ошибка: …», затем «Последняя выгрузка: дата, время · размер · блоков, пропущено, не выгружено · файлов Excel: тексты проекта, ProDiag», кнопка «⬇ ZIP» и куда положена копия архива
  • Таблица проектов «Проект · ПЛК · Выгрузка (ZIP) · Файл для ИИ»: по строке на каждый проект из tia-projects.json. «Выгрузка (ZIP)»: «⏳ выгружается…», «✓ дата, размер» или «✗ ошибка: …», кнопка «Скачать ZIP». «Файл для ИИ»: «— ждёт выгрузки», «⏳ создаётся…», «✓ готов дата, размер; N блоков, M выходов» или «✗ ошибка: причина»; кнопки «Скачать JSON» и «Пересобрать» (из последнего ZIP, без новой выгрузки из TIA)

Файл для ИИ (логика ПЛК): после каждой успешной выгрузки сайт сам, в фоне, разбирает ZIP модулем tia_logic.py и кладёт C:\tia-bridge\logic\<id проекта>.json (рядом <id>.status.json с состоянием; базы данных нет). Файл заменяется целиком: сначала пишется временный файл, потом он переименовывается, поэтому читающий никогда не увидит недописанный. Если сборка не удалась (повреждённый архив, нет блоков), прежний файл остаётся, а в окне видна причина. В файле для каждого выхода (катушка, Move, выход вызова блока) записана цепочка условий И/ИЛИ с контактами, сравнениями, таймерами и вызовами FC/FB; нераспознанное (SCL, Calc, строковые функции) помечено явно. По нему локальная модель сможет объяснить, почему встала станция. Кнопки «Скачать JSON» и «Пересобрать» видны только администратору, имя файла берётся из списка проектов, а не от клиента. Размер на WBS1 около 2 МБ. Рядом строится карта аварий <id>.alarms.json (и версия в таблице alarm_source_map): для каждого номера аварии блок, сеть, цепочка вызовов, условие и что сбрасывает; ошибка карты не ломает основной файл. В тестовой копии сайта (только чтение, READ_ONLY=1, папка /tia-bridge подключена как :ro) сборка не запускается и ничего не пишет: в колонке «🔒 недоступно в тестовой копии (только чтение)», «Пересобрать» неактивна; если файл уже лежит в logic, он показан как готовый (дата и размер по файлу) и скачивается. Если состояние записать нельзя, в окне «✗ ошибка» с причиной, а не вечное «создаётся».

Поиск проектов: служба tia-bridge.ps1 раз в минуту ищет файлы *.ap17 только в разрешённых папках (по умолчанию C:\TIA_for_claude_to_XML и C:\projects; свой список задаёт поле roots в C:\tia-bridge\tia-projects.json, правит администратор сервера), на глубину до 5 уровней, без служебных папок IM, XRef, System, Logs, Temp и без ссылок, и пишет результат в C:\tia-bridge\found-projects.json. Сайт принимает от окна только имя ПЛК и ключ найденного файла, путь с сайта не передаётся; служба ещё раз проверяет, что файл существует, это .ap17 и он внутри разрешённой папки, и сама записывает пару «ПЛК → проект» в tia-projects.json. Записи, внесённые вручную (wbs1, gwm_ub), работают как раньше. Если список старше 5 минут или службы нет, окно пишет «Список проектов устарел».

В архиве: XML блоков (OB, FB, FC, DB), типов данных (UDT) и таблиц тегов, тексты проекта на каждом языке ProjectTexts_<язык>.xlsx, контроли ProDiag ProDiag_Supervisions.xlsx и отчёт manifest.csv (строка на каждый файл: что выгружено, пропущено или с ошибкой). Архив всегда лежит в C:\tia-bridge\out (хранятся 3 последних на проект, оттуда его отдаёт «⬇ ZIP»), копия кладётся в «Путь сохранения».

Сайт работает в Linux-контейнере и не может вызвать TIA Openness (программа Windows), поэтому обмен идёт через папку C:\tia-bridge (в контейнере /tia-bridge). Сайт кладёт туда заявку, а служба tia-bridge.ps1 на этом же ПК берёт её, вызывает tia-export.ps1 (TIA Portal V17 без окна, открывается копия проекта), собирает ZIP и пишет состояние. Открытых портов нет, путь к проекту сайт не передаёт: он берётся из списка C:\tia-bridge\tia-projects.json (образец tia-projects.example.json, поле plc связывает проект с ПЛК).

Что нужно на ПК: TIA Portal V17, учётная запись Windows в группе «Siemens TIA Openness» (после добавления выйти из системы и войти снова), нужные пакеты поддержки оборудования (HSP) для устройств проекта, проект-копия, не открытая в TIA. Служба запускается задачей планировщика «PMM TIA bridge» при входе в Windows под этой учётной записью; если службы нет, в окне выгрузки написано «служба не запущена». При ошибке (например, не установлен HSP или папка недоступна) причина показывается в строке состояния окна.

Адрес без порта: IIS на порту 80 (телевизоры)

Телевизоры и любые устройства открывают PMM по адресу http://10.85.176.86 без :8000, вход Windows не нужен (прямой адрес http://10.85.176.86:8000 тоже работает). На порту 80 этого ПК работает IIS (служба W3SVC), у него два сайта, и выбирает между ними то, как набран адрес:

  • «PMM open»: адрес по IP (10.85.176.86) и любой адрес без имени. Анонимный вход, всё пересылается в PMM на 127.0.0.1:8000 (модуль ARR). Его создаёт скрипт iis-pmm-open.ps1.
  • «Default Web Site»: адрес по имени ПК (alm-amm694.mk.int, alm-amm694). Вход Windows (Negotiate/NTLM) и заготовка для входа по доменной учётке: правило в C:\inetpub\wwwroot\web.config пишет в заголовок X-Remote-User имя доменного пользователя. PMM этот заголовок пока не читает; без входа Windows этот сайт отвечает 401, и это нормально.

Запускать скрипт повторно не нужно: настройки хранятся в самом IIS и переживают перезагрузку ПК и обновления Windows. Телевизор не откроет страницу в двух случаях: 1) после перезагрузки, пока в Windows не вошла учётка MK\operator_scadabsoto (Docker Desktop запускается из неё, до этого PMM не работает и по :8000; телевизор покажет ошибку 502); 2) если в IIS кто-то удалил сайт «PMM open» или вернул сайту «Default Web Site» привязку «любой адрес» (*:80 без имени): тогда запустите скрипт ещё раз.

Скрипт запускается только от имени администратора (окно PowerShell: Пуск, найти PowerShell, правой кнопкой «Запуск от имени администратора»; в обычном окне он остановится с сообщением «Нужен запуск от имени администратора»). Перед изменениями он сохраняет копию настроек IIS (appcmd add backup pmm-before-open-site-...) и записывает прежние привязки в C:\plc-backups\iis\state.json. Сначала сухой прогон (ничего не меняет, показывает шаги):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\iis-pmm-open.ps1 -DryRun

Применить (создать сайт «PMM open», привязать прежний сайт к имени ПК):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\iis-pmm-open.ps1

В конце скрипт сам проверяет ответы: по IP и по 127.0.0.1 должно прийти {"env":"prod"} (HTTP 200), по имени ПК HTTP 401. Откат (удалить «PMM open», вернуть привязку «любой адрес» прежнему сайту):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\iis-pmm-open.ps1 -Rollback

Проверка с любого ПК в сети (если всё в порядке, придёт {"env":"prod"}; 401 или ошибка 502 значат, что сайт «PMM open» не работает или не запущен Docker):

curl.exe http://10.85.176.86/api/env

Если нужно вернуть IIS полностью как был до настройки, полная копия лежит в IIS под именем из state.json (поле backup): appcmd restore backup <имя> (программа C:\Windows\System32\inetsrv\appcmd.exe, от имени администратора).

Синхронизация времени ПЛК (NTP)

В выпадающем списке ПЛК (вкладка «ПЛК») у каждого ПЛК показано его время и расхождение с сервером PMM, например «12:41:05 · +5м 28с» (плюс означает, что ПЛК спешит, минус означает, что отстаёт). Красным цветом расхождение показывается, если оно больше 5 секунд; «—» означает, что времени нет (нет связи или ПЛК выключен из опроса). PMM читает время ПЛК раз в минуту стандартным узлом OPC UA «текущее время сервера» (i=2258) и PMM время ПЛК не меняет и ничего в ПЛК не пишет: синхронизацию делает сам ПЛК по NTP, а настраивает её пользователь в TIA Portal отдельно в каждом процессоре.

Настройка в TIA Portal (для каждого ПЛК):

  1. Откройте свойства процессора (CPU): Properties, затем Time of day.
  2. В разделе NTP mode включите «Enable time-of-day synchronization via NTP server».
  3. Укажите IP-адрес NTP-сервера (контроллер домена или сервер предприятия, который сам синхронизируется с точным временем).
  4. Задайте интервал обновления, например 60 с.
  5. Часовой пояс (UTC+5, Astana) и летнее время задаются в том же разделе Time of day.
  6. Загрузите конфигурацию в ПЛК (Download to device).

Проверка: через минуту-две в списке ПЛК расхождение меньше 5 секунд и не красное. Если расхождение осталось, проверьте, что ПЛК видит NTP-сервер по сети (адрес, шлюз, порт UDP 123 открыт).

Циклы лифтов

Вкладка «Тренды», раздел «Циклы лифтов». Цикл начинается, когда лифт стоит на 2-м уровне и вилы выдвинуты вверх (FK300.AtTop); если лифт ушёл со 2-го уровня в тот же опрос, когда поднялись вилы, цикл всё равно считается. Конец цикла: команда на отъезд (Goto3rd или Goto4th). «Ожидание, с» = от начала до команды; дольше порога: «Проблема».

«Остановка в пути» (красным): лифт поехал, команда на отъезд пропала, а целевой уровень (At3rd для Goto3rd, At4th для Goto4th) не пришёл ни в тот же опрос, ни за 5 секунд (параметр min_stop_s). Лифт стоит между уровнями, обычно с выдвинутыми вилами. В строке «Ожидание, с» показывает, сколько лифт стоял (до прибытия на любой уровень), «Последний сигнал» — сигнал разрешения, пропавший в момент остановки (в пределах ±1 с, например From GWM.ReqRevCar). Плитка «Остановок» рядом с «Проблема». На диаграмме отрезок остановки закрашен красным, добавлена дорожка EL300.ORunning (лифт едет), внизу «Лифт встал, когда пропал …, вилы выдвинуты/не выдвинуты».

Запуск при входе в систему (-OnlyIfMissing)

Задача «PMM backup» работает «только при входе пользователя», поэтому если ПК перезагрузился ночью, бэкап в 03:00 пропускается, а режим «догнать» для таких задач не срабатывает (так 19.10 пропал ночной бэкап). Поэтому у задачи два запуска: ежедневно в 03:00 и при входе пользователя, оба с параметром -OnlyIfMissing: если оба дампа за сегодня уже есть и не пустые, скрипт записывает строку в C:\plc-backups\backup.log и выходит, ничего не делая и не трогая status.json. Команда, которая переключает задачу (выполнить в PowerShell администратором):

Set-ScheduledTask -TaskName 'PMM backup' -Action (New-ScheduledTaskAction -Execute 'powershell.exe' -Argument '-NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\backup.ps1 -OnlyIfMissing') -Trigger @((New-ScheduledTaskTrigger -Daily -At 3am), (New-ScheduledTaskTrigger -AtLogOn -User 'MK\Operator_SCADABSOTO'))

Проверка: Get-ScheduledTask 'PMM backup' показывает два триггера (Daily и Logon), в действии виден -OnlyIfMissing.

🚀 Перенос на другой ПК (с базой, пользователями и настройками)

Все команды запускаются в PowerShell. Проверено: дамп базы восстанавливается на чистом сервере без потерь (пользователи, простои, план, настройки, теги ПЛК совпали по числу строк).

Требования к новому ПК

  • Windows 11 Pro, Docker Desktop (WSL2) и Git установлены; Docker Desktop запускается при входе в систему
  • Тот же сетевой доступ к ПЛК: адреса ПЛК (OPC UA) хранятся в базе и должны быть доступны с нового ПК
  • Постоянный (статический) IP-адрес, выключенный спящий режим, свободные порты 8000, 5432, 3000, 5678
  • Местное время завода задаёт параметр KPI_UTC_OFFSET_HOURS в docker-compose.yml: на сколько часов местное время отличается от UTC (сейчас 5, то есть UTC+5). Он определяет границы смен и суток (когда начинается новый день и интервалы), время на экранах Andon и время автосохранения отчётов. Часы самого ПК и пояс Windows на это не влияют. Если новый ПК стоит на том же заводе, ничего менять не нужно (значение переносится с кодом). Если пояс другой, измените число в обоих местах (fastapi-api и plc-monitoring-docker-poller) и перезапустите контейнеры
⚠ Выполняйте команды по одной. Вставляйте и запускайте каждую строку отдельно и дожидайтесь результата. Если две команды склеились в одну строку (например, git pushdocker compose stop …), ни одна из них не выполнится, а на экране это легко не заметить.

🔧 Решение проблем

❌ Команда «не сработала», хотя ошибки нет

  • Проверьте, не склеились ли две команды в одну строку (например, git pushdocker compose stop): вставляйте и запускайте по одной
  • После остановки проверьте результат: docker ps; после git push: git status -sb (не должно быть ahead)

❌ Команда «не сработала», хотя ошибки нет

  • Проверьте, не склеились ли две команды в одну строку (например, git pushdocker compose stop): вставляйте и запускайте по одной
  • После остановки проверьте результат: docker ps; после git push: git status -sb (не должно быть ahead)

❌ Контейнеры не запускаются

  • Проверьте, запущен ли Docker Desktop
  • Проверьте порты: не занят ли 5432, 8000, 5678, 3000
  • Просмотрите логи: docker compose logs

❌ БД не инициализируется

  • Остановите контейнеры (docker compose down) и переименуйте папку pg_data (данные базы лежат в ней; сначала сделайте дамп, если база уже работала)
  • Пересоздайте контейнеры: docker compose down && docker compose up -d

❌ Веб-интерфейс показывает старый код

  • Очистьте кэш браузера: Ctrl+Shift+R
  • Или пересоберите контейнер: docker compose build --no-cache fastapi-api && docker compose up -d fastapi-api

❌ ПЛК не подключается

  • Проверьте адрес ПЛК (OPC UA) во вкладке «ПЛК» и доступность ПЛК по сети с этого ПК
  • Убедитесь, что ПЛК в сети и включена OPC UA
  • Посмотрите логи Poller: docker logs python-async-poller

Версия проекта: 1.0.0

Сборка: Иерархический браузер переменных + поиск по Data Block (Instance & Global) + кэширование БД

Global Data Blocks: Автоматическое обнаружение (Namespace 3), кэширование, поиск и фильтрация по 1100+ переменным

Структурные теги (массивы и структуры, как в WinCC): раскрываются по клику ▷, вложенные элементы подгружаются с ПЛК через API /api/plcs/{id}/opcua/children

Галочка у переменной сразу сохраняет её в БД (таблица plc_tags, тип DIGITAL/ANALOG определяется по типу данных ПЛК), снятие галочки отключает тег; столбцы «Архив», «Grafana», «Оповещение»; «Выбрать все» в шапке столбца, маркер заполнения у ячейки (протяжка вниз или вверх, как в Excel) и Shift+клик по диапазону меняют флажки сразу у многих строк одним пакетом. Кнопки «Обновить с ПЛК» и «Из БД» находятся в панели Data Blocks, там же дата и время последнего сканирования

Колонка «Значение» показывает текущие значения переменных из ПЛК в реальном времени: раз в секунду читаются только видимые на экране строки (до 80), пакетным запросом через POST /api/plcs/{id}/opcua/values; значок LIVE в заголовке области «Переменные» показывает состояние обновления, при чтении также определяется тип данных

Вкладка «Andon / KPI» (Dashboard, информационная панель) повторяет KPI-экраны SCADA: для выбранного ПЛК находит блоки почасового счётчика кузовов (*_counting_numbers_of _Body_by_the_hours_DB), по кнопкам выбирается линия (GWM, Chery, Changan). Таблица: интервал, минуты, план, количество кузовов, отклонение, Takt Time, итого и средний такт смены; слева текущий такт между кузовами; дата и время — с сервиса на ПК (GET /api/time, смещение KPI_UTC_OFFSET_HOURS), а не часы браузера телевизора. Обновление раз в секунду. Начало интервалов берётся из ПЛК, окончание и план задаются кнопкой «Смена и план» и хранятся в таблице kpi_schedule (создаётся автоматически при запуске API)

Переменные блока показываются плоским нумерованным списком; в OPC UA видны только переменные с флагом «Accessible from HMI/OPC UA» в TIA Portal
