📊 Архитектура проекта

PMM (Production Monitoring & Management) — система мониторинга и управления производством: опрос ПЛК, доска Andon/KPI, простои, отчёты, графики, тренды. Система состоит из нескольких компонентов, которые работают в Docker контейнерах:

Порядок вкладок и списков

Порядок вкладок и списков меняется перетаскиванием, хранится у каждого пользователя; администратор с Shift задаёт порядок по умолчанию.

Дни без выпуска и «Простой весь день (поломка линии)»

Если за закрытый день (раньше сегодняшнего по времени сервера) на линии не произведено ни одного кузова, это выходной или нет плана: автоматический простой и «не описано» за этот день не считаются нигде (Andon и его архив, «Простои», «Графики», «Отчёты», Excel, автосохранение). Строка дня остаётся в таблице «По дням» (план и факт 0, строка выделена), но в план, факт, % выполнения и «Дней с данными» периода и на график план-факт такой день не входит; «±» не показывается, вместо простоя подпись «нет выпуска». Текущий день правило не применяет. Простои, которые люди уже описали, остаются и считаются. Правило одно на сервере (dayflags.py), экраны только читают его результат. У подсборок (ручной ввод) правило действует, когда по интервалам введены факты и их сумма равна нулю.

Если линия в такой день стояла из-за поломки, во вкладке «Отчёты» (один день, одна линия) нажмите «Простой весь день (поломка линии)»: время простоя дня пойдёт в статистику как у рабочего дня. Кнопка видна только для закрытого дня без выпуска и только тем, кто может править (кроме роли «Просмотр»); поставить отметку можно только для такого дня, иначе сервер ответит 409. Снять отметку может автор и администратор. Каждое изменение пишется в журнал kpi_day_flags_log (кто, когда, было, стало); таблицы kpi_day_flags и журнал создаются при старте API сами. Изменение видно на всех экранах не позднее чем через 5–10 секунд.

Среда: разработка и рабочая (APP_ENV)

Запись в ПЛК (сейчас это «план на день» на экранах Finish Line) разрешена только в рабочей среде. Переменная APP_ENV по умолчанию dev (запись запрещена, в шапке сайта метка «Среда: разработка»). На сервере в папке проекта рядом с docker-compose.yml нужно создать файл .env со строкой APP_ENV=prod (в Git он не попадает) и пересоздать контейнеры. Если файл забыт, запись плана FL не пройдёт с сообщением «Режим разработки: запись в ПЛК отключена», сами ПЛК не пострадают.

Обновление сервера одной командой

Нажмите «Скопировать», откройте PowerShell на сервере (Пуск, набрать PowerShell, от имени администратора), вставьте команду правой кнопкой мыши или Ctrl+V и нажмите Enter. Команды выполняйте по одной.

Первый раз (когда файла update-server.ps1 на сервере ещё нет): сначала вручную git pull в папке проекта, затем запустите скрипт с ключом -Force (он пересоберёт образы, даже если версия уже последняя). Дальше обычный запуск без ключей.

Первый раз, шаг 1: перейти в папку проекта, затем получить новую версию (две отдельные команды, по одной):

cd C:\plc-monitoring-docker-poller
git pull

Первый раз, шаг 2: запуск с ключом -Force:

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\update-server.ps1 -Force

Скрипт update-server.ps1 в корне проекта обновляет рабочий сервер без ручных шагов. По порядку: проверяет окружение (git, docker, папка проекта); запоминает текущий коммит; всегда делает бэкап (backup.ps1, без свежего успешного бэкапа обновление не начинается); останавливается, если изменены отслеживаемые файлы (кроме n8n_data и grafana_data); получает новую версию через git pull --ff-only (если версия уже последняя, пересборки нет); создаёт или правит .env со строкой APP_ENV=prod; пересобирает образы fastapi-api и plc-monitoring-docker-poller; запускает их (база и остальные сервисы не пересоздаются); до 90 секунд проверяет, что контейнеры работают, /api/env отвечает prod, а /api/plcs отдаёт список ПЛК.

Запуск (одна команда):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\update-server.ps1

Проверка результата: в конце окна написано «Обновление завершено успешно» и показаны прежний и новый коммит. Контейнеры можно проверить командой:

docker ps

Пробный запуск без изменений (только печатает, что было бы сделано):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\update-server.ps1 -DryRun

Ярлык на рабочем столе сервера (одна команда в PowerShell):

$s = (New-Object -ComObject WScript.Shell).CreateShortcut("$env:USERPROFILE\Desktop\Обновить PMM.lnk"); $s.TargetPath = "powershell.exe"; $s.Arguments = '-NoProfile -ExecutionPolicy Bypass -File "C:\plc-monitoring-docker-poller\update-server.ps1"'; $s.WorkingDirectory = "C:\plc-monitoring-docker-poller"; $s.Save()

Проверка: на рабочем столе появился ярлык «Обновить PMM»; окно после запуска не закрывается, пока не нажать Enter.

Откат. Если сборка, запуск или итоговая проверка не прошли, скрипт сам возвращает прежний коммит (git reset --keep, живые файлы n8n_data не затираются), заново собирает и запускает прежнюю версию и пишет «ОТКАТ ВЫПОЛНЕН: работает прежняя версия …» или «ОТКАТ НЕ УДАЛСЯ: нужна ручная проверка» с командами диагностики. Если не прошли шаги до получения новой версии, ничего не менялось, откат не нужен. Журнал каждого запуска сохраняется в C:\plc-backups\update-logs.

Копирование отчётов в сетевую папку

Скрипт copy-reports.ps1 в корне проекта копирует новые и изменённые файлы *.xlsx из локальной папки отчётов (C:\Andon-Reports, вместе с подпапками «год-месяц» и линий) в сетевую папку через robocopy. Структура подпапок сохраняется, в сетевой папке ничего не удаляется. Журнал пишется в C:\plc-backups\update-logs\copy-reports-ГГГГ-ММ-ДД.log. Код выхода 0 означает успех, 1 означает ошибку (сетевая папка недоступна или robocopy вернул 8 и больше). Сетевую папку в контейнер не подключаем: копирует хост.

Пробный запуск (ничего не копирует, только проверяет, что обе папки доступны):

powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\copy-reports.ps1 -DryRun -NoPause

Ежедневная задача планировщика на сервере (одна команда в PowerShell от имени администратора). Задача должна идти под учётной записью, у которой есть доступ к сетевой папке: запускайте команду под ней, без параметра /RU SYSTEM (учётная запись SYSTEM к сетевой папке доступа обычно не имеет):

schtasks /Create /SC DAILY /ST 23:50 /TN "PMM copy reports" /TR "powershell -NoProfile -ExecutionPolicy Bypass -File C:\plc-monitoring-docker-poller\copy-reports.ps1 -NoPause"

Проверка: задача есть в списке, у неё указано время следующего запуска.

schtasks /Query /TN "PMM copy reports"

Время 23:50 выбрано позже автосохранения отчётов (оно идёт в заданное для линии время в экране «Отчёты»), чтобы в сетевую папку попал уже готовый файл дня. Автосохранение пишет один файл в день на линию с одним листом «Отчёт»: сверху отчёт дня, ниже отчёт с начала месяца по этот день.

Выгрузка проектов TIA Portal в XML

Во вкладке «Переменные ПЛК» (только администратор) есть панель «Проекты TIA»: таблица разрешённых проектов с галочками, «выбрать все» и кнопкой «Выгрузить выбранные». Кнопка запускает выгрузку каждого проекта в XML (блоки OB, FB, FC, DB, типы данных, таблицы тегов и manifest.csv), готовый архив скачивается кнопкой «⬇ ZIP». Проект не меняется и не сохраняется.

Сайт работает в Linux-контейнере и не может вызвать TIA Openness (программа Windows), поэтому обмен идёт через папку C:\tia-bridge (в контейнере /tia-bridge). Сайт кладёт туда заявку, а служба tia-bridge.ps1 на этом же ПК берёт её, вызывает tia-export.ps1 (TIA Portal V17 без окна, открывается копия проекта), собирает ZIP и пишет состояние. Открытых портов нет, путь к проекту сайт не передаёт: он берётся из списка C:\tia-bridge\tia-projects.json (образец tia-projects.example.json).

Что нужно на ПК: TIA Portal V17, учётная запись Windows в группе «Siemens TIA Openness» (после добавления выйти из системы и войти снова), нужные пакеты поддержки оборудования (HSP) для устройств проекта, проект-копия, не открытая в TIA. Служба запускается задачей планировщика «PMM TIA bridge» при входе в Windows под этой учётной записью; если службы нет, рядом с панелью написано «служба не запущена». При ошибке (например, не установлен HSP) причина показывается в столбце «Состояние».

Синхронизация времени ПЛК (NTP)

В выпадающем списке ПЛК (вкладка «Переменные ПЛК») у каждого ПЛК показано его время и расхождение с сервером PMM, например «12:41:05 · +5м 28с» (плюс означает, что ПЛК спешит, минус означает, что отстаёт). Красным цветом расхождение показывается, если оно больше 5 секунд; «—» означает, что времени нет (нет связи или ПЛК выключен из опроса). PMM читает время ПЛК раз в минуту стандартным узлом OPC UA «текущее время сервера» (i=2258) и PMM время ПЛК не меняет и ничего в ПЛК не пишет: синхронизацию делает сам ПЛК по NTP, а настраивает её пользователь в TIA Portal отдельно в каждом процессоре.

Настройка в TIA Portal (для каждого ПЛК):

  1. Откройте свойства процессора (CPU): Properties, затем Time of day.
  2. В разделе NTP mode включите «Enable time-of-day synchronization via NTP server».
  3. Укажите IP-адрес NTP-сервера (контроллер домена или сервер предприятия, который сам синхронизируется с точным временем).
  4. Задайте интервал обновления, например 60 с.
  5. Часовой пояс (UTC+5, Astana) и летнее время задаются в том же разделе Time of day.
  6. Загрузите конфигурацию в ПЛК (Download to device).

Проверка: через минуту-две в списке ПЛК расхождение меньше 5 секунд и не красное. Если расхождение осталось, проверьте, что ПЛК видит NTP-сервер по сети (адрес, шлюз, порт UDP 123 открыт).

Требования к новому ПК

  • Windows 11 Pro, Docker Desktop (WSL2) и Git установлены; Docker Desktop запускается при входе в систему
  • Тот же сетевой доступ к ПЛК: адреса ПЛК (OPC UA) хранятся в базе и должны быть доступны с нового ПК

  • Местное время завода задаёт параметр KPI_UTC_OFFSET_HOURS в docker-compose.yml: на сколько часов местное время отличается от UTC (сейчас 5, то есть UTC+5). Он определяет границы смен и суток (когда начинается новый день и интервалы), время на экранах Andon и время автосохранения отчётов. Часы самого ПК и пояс Windows на это не влияют. Если новый ПК стоит на том же заводе, ничего менять не нужно (значение переносится с кодом). Если пояс другой, измените число в обоих местах (fastapi-api и plc-monitoring-docker-poller) и перезапустите контейнеры
⚠ Выполняйте команды по одной. Вставляйте и запускайте каждую строку отдельно и дожидайтесь результата. Если две команды склеились в одну строку (например, git pushdocker compose stop …), ни одна из них не выполнится, а на экране это легко не заметить.

Откат, если что-то пошло не так

Старый ПК остаётся нетронутым (шаг 2 лишь остановил контейнеры): выполните на нём docker compose up -d, а на новом docker compose down. Потеряются только данные, накопленные после остановки.

Безопасность после переноса

  • Адрес репозитория (git remote -v) не должен содержать токен GitHub: храните доступ в «Диспетчере учётных данных» Git. Если токен был открыт в адресе, его нужно отозвать на GitHub и выпустить новый
  • Пароль базы my_strong_password в docker-compose.yml стоит заменить на свой (изменить в docker-compose.yml, python-async-poller/.env и пользователе PostgreSQL); сделайте это отдельным шагом после проверки переноса
  • Порты 5432 (база), 3000 (Grafana) и 5678 (N8N) без надобности не открывайте в брандмауэре для сети

🔧 Решение проблем

❌ Команда «не сработала», хотя ошибки нет

  • Проверьте, не склеились ли две команды в одну строку (например, git pushdocker compose stop): вставляйте и запускайте по одной
  • После остановки проверьте результат: docker ps; после git push: git status -sb (не должно быть ahead)

❌ Команда «не сработала», хотя ошибки нет

  • Проверьте, не склеились ли две команды в одну строку (например, git pushdocker compose stop): вставляйте и запускайте по одной
  • После остановки проверьте результат: docker ps; после git push: git status -sb (не должно быть ahead)

❌ Контейнеры не запускаются

  • Проверьте, запущен ли Docker Desktop
  • Проверьте порты: не занят ли 5432, 8000, 5678, 3000
  • Просмотрите логи: docker compose logs

❌ БД не инициализируется

  • Остановите контейнеры (docker compose down) и переименуйте папку pg_data (данные базы лежат в ней; сначала сделайте дамп, если база уже работала)
  • Пересоздайте контейнеры: docker compose down && docker compose up -d

❌ Веб-интерфейс показывает старый код

  • Очистьте кэш браузера: Ctrl+Shift+R
  • Или пересоберите контейнер: docker compose build --no-cache fastapi-api && docker compose up -d fastapi-api

❌ ПЛК не подключается

  • Проверьте адрес ПЛК (OPC UA) во вкладке «Переменные ПЛК» и доступность ПЛК по сети с этого ПК
  • Убедитесь, что ПЛК в сети и включена OPC UA
  • Посмотрите логи Poller: docker logs python-async-poller

Версия проекта: 1.0.0

Сборка: Иерархический браузер переменных + поиск по Data Block (Instance & Global) + кэширование БД

Global Data Blocks: Автоматическое обнаружение (Namespace 3), кэширование, поиск и фильтрация по 1100+ переменным

Структурные теги (массивы и структуры, как в WinCC): раскрываются по клику ▷, вложенные элементы подгружаются с ПЛК через API /api/plcs/{id}/opcua/children

Галочка у переменной сразу сохраняет её в БД (таблица plc_tags, тип DIGITAL/ANALOG определяется по типу данных ПЛК), снятие галочки отключает тег; столбцы «Архив», «Grafana», «Оповещение»; «Выбрать все» в шапке столбца, маркер заполнения у ячейки (протяжка вниз или вверх, как в Excel) и Shift+клик по диапазону меняют флажки сразу у многих строк одним пакетом. Кнопки «Обновить с ПЛК» и «Из БД» находятся в панели Data Blocks, там же дата и время последнего сканирования

Колонка «Значение» показывает текущие значения переменных из ПЛК в реальном времени: раз в секунду читаются только видимые на экране строки (до 80), пакетным запросом через POST /api/plcs/{id}/opcua/values; значок LIVE в заголовке области «Переменные» показывает состояние обновления, при чтении также определяется тип данных

Вкладка «Andon / KPI» (Dashboard, информационная панель) повторяет KPI-экраны SCADA: для выбранного ПЛК находит блоки почасового счётчика кузовов (*_counting_numbers_of _Body_by_the_hours_DB), по кнопкам выбирается линия (GWM, Chery, Changan). Таблица: интервал, минуты, план, количество кузовов, отклонение, Takt Time, итого и средний такт смены; слева текущий такт между кузовами; дата и время — с сервиса на ПК (GET /api/time, смещение KPI_UTC_OFFSET_HOURS), а не часы браузера телевизора. Обновление раз в секунду. Начало интервалов берётся из ПЛК, окончание и план задаются кнопкой «Смена и план» и хранятся в таблице kpi_schedule (создаётся автоматически при запуске API)

Переменные блока показываются плоским нумерованным списком; в OPC UA видны только переменные с флагом «Accessible from HMI/OPC UA» в TIA Portal
